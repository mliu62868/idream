# Admin 产品与运营体检清单（Chrome 执行版）

编制日期：2026-09-13。用途：下一轮逐项检查 Admin 功能完整性、业务逻辑和运营闭环。**本文是验收规格，不是已通过报告；所有检查项初始均为未执行。**

## 1. 结论与判断原则

Admin 应让运营把“发现问题或机会”推进到“用户得到正确结果”，并证明内容、权限、交付和账务一致。功能完整不能按菜单数量判断，必须覆盖 **发现 → 理解 → 决策 → 执行 → 验证 → 恢复/复盘**。

从第一性原理看，平台需要持续供给有吸引力的成年角色，让用户发现、创建、聊天和创作；兑现付费承诺；处理失败与争议；再用可信反馈改进供给和体验。由此推导以下后台责任：

| 业务责任 | 产品经理要回答 | 运营经理要完成 | 验收输出 |
| --- | --- | --- | --- |
| 角色供给 | 人设、形象、声音及上线版本是否一致？ | 创建、补素材、预览、发布、暂停、恢复 | 用户实际看到并使用指定版本 |
| 内容分发 | 什么内容向谁、何时、在哪里展示？ | 上传、排位、公告、CMS、撤下 | 目标用户可见，非目标用户不误见 |
| 用户服务 | 用户遇到阻断能否恢复原任务？ | 找人、查单、认领、处理、回复、追踪 | 用户侧结果与工单结论相符 |
| 收入与权益 | 收款、权益、消耗、退款是否守约？ | 查账、核对、调整、促销、追踪异常 | 原交易、权益快照、账本可对账 |
| 可靠交付 | 技术成功是否真正交付给用户？ | 定位失败、恢复原请求、处理事故 | 产物可用且不重复执行/收费 |
| 平台治理 | 谁能看什么、改什么、为谁负责？ | 授权、审批、审计、隐私请求 | 权限由服务端执行，动作可追溯 |
| 经营学习 | 数字是否可用于决策？ | 看漏斗、留存、质量、成本和实验 | 可解释口径、可核对事实、明确不确定性 |
| 完整平台扩展 | 社区、联盟和作品权益是否有完整运营支撑？ | 管理创作者、归因、佣金、作品与争议 | 新产品不会只有用户入口而无运营闭环 |

每个写操作须回答六个问题：改哪个对象、前置条件是什么、影响谁、何时生效、失败如何恢复、到哪里核验。角色日常制作无需人为增加负责人、排期、手工 QA 或审批；Case、Incident 等需要协作的任务仍须可分派和追踪。

### 2.2 已定边界，禁止按旧方案误判

1. `MODERATION_PROVIDER=mock`、保留但不启用 `safety-gateway` 是既定配置；不列为功能缺口。仍检查 `underage/minor/csam` 基础拦截、角色年龄至少 18 岁、举报、申诉和权限。只使用安全测试文本，不制作违规素材。
2. 日常角色图片采用“创建 → 生成或上传 → 选择采用 → 预览 → 发布”，不恢复旧人工打分、逐图审批或虚构五轮 QA。举报后的违规处置是独立流程。
3. 非角色运营图片从外部制作后上传、进入素材库与草稿投放；不恢复 Admin 通用生图。生成历史需要可查。
4. Chat 使用自托管开源 OpenAI-compatible 模型；Gen 使用 workflow-native backend。退役 `pipeline/mlx/external` runner 不作为兼容面验收。
5. 视频按 capability、环境开关、合格 workflow/profile、角色来源、价格与权益共同开放。H3 的既有技术交付不代表质量合格，不为了跑清单强行重新启用。
6. 计划是一次性预付周期访问，不按自动续订产品验收；到期不锁回既有聊天、媒体或已购作品。图片/视频只有 dreamcoin 消耗，不另造独立配额；语音保留计划分钟及超额报价。
7. WPCU 保持 official；WSCU/WSCrU/WPSCU/WSR 是诊断。没有成熟样本、合格事实或认证时，显示不可用于决策比显示漂亮数字更正确。
8. 完整平台目标仍包含 Group Chat、Voice Call、Packs、Comics、Creator Economy 与 Affiliate。当前缺入口须记范围缺口；已关闭且如实说明的能力可通过“曝光边界”检查，但不能因此通过“功能实现”检查。
9. 旧文档与上述决策冲突时使用最新明确决策；遇到没有决策依据的冲突，记“待澄清”，不能按代码现状自动缩减目标。

已定位的具体冲突：[经济规格 §4.2](ECONOMY_AND_PRICING.md) 仍将访问计划争议/人工退款笼统写成 `admin_adjust`；[账务架构 §7](../architecture/08-billing-and-entitlements.md) 已明确正常已结算预付访问的全额退款使用专门 provider refund、冻结权益并精确冲销本次 grant。本清单按后者的专门流程验收，人工币补偿单独检查；旧泛化说明应另行修订，不据此把正确退款逻辑报成缺陷。

## 3. Chrome 检查怎么执行

### 3.1 两层证据与结果字段

表中证据类型：**A**＝Admin 页面、Chrome Network/Console 与刷新读回；**U**＝另一个用户会话/无痕窗口在 Main 复验；**E**＝工程协作提供同版本权威记录、日志、账本或 provider 回执。A 中的成功提示和 HTTP 200 不能替代 U/E。

每个检查 ID 均创建一条结果记录；一行有多个动作或分支时拆为 `ID-a/b/c`，全部通过才勾选父项。记录模板：

| 检查 ID/分支 | 实现状态 | 执行结果 | 环境/source/时间 | 账号权限与测试对象 ID | 实际步骤和结果 | 截图/请求/权威证据 | 问题/负责人/复验 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 例如 CH-01-a | 待核对 | 未执行 | 待填 | 待填 | 待填 | 待填 | 待填 |

- 实现状态：待核对 / 已有可执行能力 / 部分实现 / 缺入口或能力 / 条件关闭 / 仅工程工具。不要把这些状态当作验收结果。
- 执行结果：未执行 / 通过 / 失败 / 阻塞 / 不适用。不适用必须有产品或环境依据；无测试数据记阻塞，不能记通过。
- 未实现目标项记“缺入口或能力”，关联产品缺口；不是假装点过后报告运行 bug。
- 涉及工程证据的条目，A/U 通过但 E 未提供时只记分支通过，父项仍未完成。
- 问题记录遵循[分诊状态](../agents/triage-labels.md)；检查结果字段不是新的事项分诊体系。

## 9. 执行顺序、收口与交付标准

### 9.1 建议轮次

1. **入口与权限轮**：PRE、G 的公共读项、§4 全部目的地、TD、AUTH。先找断链、空壳、无法授权和只显示成功的页面。
2. **供给与内容轮**：CH/CT/IM/VO/RL/CO/CMS，走 F-01～08；建立后续用户链需要的测试内容。
3. **用户与履约轮**：CU/CS/FB/MD/AC/BL/PR/PM，走 F-09～14；真实支付与删除按独立授权范围。
4. **异常恢复轮**：GN/CHAT/IN/OP/GV，走 F-15～17、F-20；由工程准备明确的失败/未知/并发样本。
5. **经营与完整平台轮**：MT/EX/EXT，走 F-18～19、F-21～23；缺能力、缺成熟时间与未认证逐项保留。

同一时间只让一个操作者驱动 Chrome 与 dev server；各轮保持同版本或明确重新验证受改动影响的条目。不能把不同 source 的分支拼成“同版本全部通过”。

### 9.2 问题判定

- **产品经理判定**：该能力是否承接明确用户价值；菜单/按钮的承诺是否兑现；完整需求是否被覆盖；状态和权益语义是否正确。
- **运营经理判定**：无需开发代操作是否能发现、定位、处理和验证；有否合理异常出口；权限、交接、筛选、批量与审计能否支撑日常工作。
- **工程补证**：跨服务原子性、并发、持久化、provider、账务和指标必须有 E 证据。需要开发协作取证不自动算缺陷；正常运营动作长期只能写 SQL/API 则是运营能力缺口。
- 发现缺陷按“现象 → 前提 → 最短复现 → 预期/实际 → 证据 → 用户/运营影响 → 负责人”记录。产品冲突另列待澄清；不把未执行推定为失败。
