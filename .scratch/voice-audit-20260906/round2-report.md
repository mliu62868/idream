# 角色声音：从第一性原理继续改进

日期：2026-09-06。本轮接续第一轮审计，重点是声音身份和运营确认在并发、刷新、重试时保持一致。

## 设计判断

声音系统最核心的责任是：运营确认哪一个声音版本，下一次实际生成就使用一个明确、可追溯的声音身份；已交付音频保持原资产和原计费事实。

因此保留三层规则：

1. 角色有已启用的专属音色时，固定使用该 profile 的 provider、voice ID 和演绎设置。
2. 没有专属音色时，按已保存的系统默认映射选声。性别映射只是默认分配规则，不意味着根据性别就能确定音色偏好；角色专属选择优先。
3. 生成请求创建时冻结身份。后续启用、恢复默认、修改全局默认都不改写旧请求或旧音频。

不根据音色名称推测声音特征，不把英语目录可用等同于中文声音质量达标。本轮不改现有 Alba 默认映射。

## 本轮发现与修复

### 1. 后端读取发生在不同时间，可能生成错误身份

原流程先做角色访问权限读取，拿到 voiceId=A。若 Admin 随后原子启用 B，A 已归档，而声音 resolver 仍拿旧 A 查询当前 active，找不到后就误用系统默认。这会把错误声音永久写入 VoiceClipRequest。

改为 resolver 只接收 characterId，从同一个 PostgreSQL RepeatableRead 短事务读取角色指针、性别、匹配的 active profile 及系统默认。事务不包含模型请求或运行时健康检查。Admin 工作区直接消费同一份声音权威投影，避免重复拼接出另一个结论。

新增真实数据库交错测试先复现失败：预期角色 B，实际持久化为 Alba/system_default/profileVersion=null。修复后启用 B 与恢复默认两个交错场景通过。

### 2. 运营审核意图会被刷新替换

- 候选被其他人替换后，原启用原因仍保留，可能直接启用未审核的新候选。
- 当前声音或将继承的默认变更后，原恢复原因仍可套用到新的操作对象。

改为审核原因绑定角色、候选和当前声音/默认版本。对象变更后清空对应原因，要求重新核对；后端原有 CAS 仍负责拒绝提交期间的竞争。

### 3. 全局默认草稿和确认内容不稳定

- 收到新版本后原编辑草稿会被静默覆盖。
- 确认框的提交内容跟随刷新变化，响应丢失后的重试可能变成另一个请求。

改为保留过期草稿，明确提示并禁用保存，提供“放弃草稿并载入当前默认”。确认框固定 provider、版本、四项音色映射和演绎，展示实际待提交值。即使收到更新后的页面数据，同一次确认仍提交原快照与原幂等键，让后端选择重放成功回执或返回版本冲突。

权限在确认期间撤销时，明确显示失败并保留对话框，不再关闭后假装保存结束。补齐不可试听提示的中文翻译。
