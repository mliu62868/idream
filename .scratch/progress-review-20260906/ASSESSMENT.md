# iDream 当前进度与下一阶段方向

日期：2026-09-06。性质：产品与架构分析，未实施业务改动。

## 核心判断

iDream 已有较完整的核心产品实现和多轮受控本地交付证据，正处于从“功能可用”走向“体验稳定、能够经营”的阶段。下一阶段建议以**默认核心链路的质量、速度和回访价值**为主线，辅以稳定验收基线与可信指标，再按既定阶段补真实商业闭环和完整平台能力。

不能用一个完成百分比描述当前状况：PRD 阶段 A 的真实购买与权益还没有完整验收，而阶段 B 的视频、声音、编辑增强和部分社区能力已经提前实现。工程完成度、体验成熟度、经营验证和生产认证是不同维度。

本轮没有发现需要推翻 Main / Chat / Gen 架构的证据。主要风险位于共享设备容量、跨服务结果恢复、较大的前端工作区、持续变化的开发环境，以及产品质量和经营证据不足。

## 最关键的五个判断

### 1. 工程可靠性进步明显，产品吸引力仍缺系统证据

已有大量有价值的验证证明了“交付真的落库”“失败不重复扣费”“改声音不改旧音频”“重生成保持历史版本”。这些是成立的工程资产。它们还没有回答：角色是否有区别、用户是否愿意聊下去、图是否值得保存、明天是否回来。

9 月 5 日 Chat 事实保真样本从 8/12 改到 12/12，说明小型固定样本能发现并改进问题；它不是完整角色质量认证。9 月 6 日声音业务链通过，但报告明确未评估音色吸引力、复制相似度、中文自然度、长文本或并发。

建议从现有库存选 5 个差异明确的角色，固定 Soul、视觉与声音版本。每个覆盖初识、跨会话回忆、剧情推进、图片要求、局部编辑、语音和错误恢复。评价角色区分度、事实保真、自然度、画面身份与构图、声音匹配及完成任务的耗时。模型版本使用离线样本评估；日常发布延续自动检查与显式发布。

本地聚合显示 15 个 official/public/approved/live 角色记录。这只是内容库存信号，不是最终目录可见数、精品角色数或用户偏好证明。当前更值得精修已有角色并取得体验反馈。

### 2. 生成性能已经是产品瓶颈，优化目标要覆盖完整等待

9 月 5 日独立执行记录：

| 样本 | 历史记录 | 正确解释 |
| --- | --- | --- |
| 首张图片 | 153.2 秒 | 约 2.6 分钟，单次样本 |
| 身份/场景图片 | 331.959、368.909、390.14 秒 | 约 5.5–6.5 分钟，不能当成 p95 |
| 5 秒 RedGraft 视频 | 955.711 秒实际执行 | 约 15.9 分钟，尚不含全部排队 |
| 一次短 Chat | 18.05 秒，32 输出 tokens | 总完成耗时，不是首字时间 |
| Pocket / Fish 短声音 | 486 / 2974 ms | 9 月 6 日分别生成 3.28 / 3.90 秒音频；不能外推长文本和高并发 |

图片与视频通过 `generation-accelerator-lease.ts` 的主机文件锁串行执行。此前确有模型实验占锁、产品任务长时间等待和超时恢复事件；相关等待/执行计时修复已经完成，不能再列为未修复问题。Chat 在同一高负载时出现首字超时，记录只支持同时发生，尚未证明唯一因果。

下一步应分别测量：排队、模型装载、推理、编码、传输、可见交付，以及同主机负载对 Chat 的影响。先取得冷/热与混合负载的基线，再调整实际瓶颈。容量锁有保护价值；扩大 worker 数不等于增加物理算力。

本地单机若达不到目标，应以测量结果决定运行时资源隔离、独立设备或其他部署方式。完整成本包括设备占用与失败返工，本地无 API 账单不代表成本为零。服务端已有公平调度需求时再加入相应能力，避免先建通用调度平台。

9 月 6 日 H3 MLX 实验相对较早 ComfyUI 记录仅有 1.63% 的单样本差异，报告不认定稳定领先，且用户已决定保留 ComfyUI。该记录支持当前继续优化既有线路；不支持再把换框架作为默认下一步。原实验材料已清理，报告数字属于历史总结。

### 3. 架构方向合理，下一轮应沿真实变化边界优化

当前责任分配应继续保持：

| 边界 | 唯一职责 |
| --- | --- |
| Main PostgreSQL | 用户、角色、Release / Serving、产品 Turn、交付、用量、账本与运营命令 |
| Chat / DSH / igrep | 接收不可变快照、执行模型与工具、保留未决终态候选；记忆是已提交事实的投影 |
| Gen | 模型执行、原始产物、执行与终态证据 |
| Admin | 运营工作区，通过受保护接口操作 Main 权威 |
| Shared | 跨边界的合同、校验与幂等身份 |

抽查确认：Chat 先保存 proposal，再提交 Main；校验 durable ACK 后推进完成。声音从同一 RepeatableRead 数据库快照解析当前指针、profile 与默认。这些处理的是现实的持久化和竞争问题，有明确价值。

后续结构优化重点是用户工作区和业务入口：当前 `service.ts` 约 4993 行，`GeneratorWorkspace.tsx` 约 4629 行，`CharacterAssetStudio.tsx` 约 2490 行，`ProfileWorkspace.tsx` 约 2179 行。行数只用于定位，不是缺陷结论。生成工作区的表单、报价、未知提交恢复、任务观察与素材选择，以及 service 内发现/创建/生成/媒体等多域入口，是修改相关功能时值得检查的边界。按业务输入输出原位提取，保留幂等与恢复行为。

没有证据支持此时增加 Main 微服务拆分、第二个 Chat 数据库或 Agent runtime。优先把现有事实链跑稳，并让一次局部修改不需要理解整个页面与服务。

### 4. 当前缺的是经营证据，指标基础设施并非没做

本地 `metric_snapshots` 查询结果为 0；源码中缺 snapshot 会阻止指标被认证为可用于决策。这是诚实的不可用状态，不能为了仪表盘有数字而绕过认证。

本地存在 customer / internal / fixture / audit 多类账号。customer 标签本身不能证明是真实外部用户。订阅与 checkout 还有 mock、BTCPay 历史记录，provider 字段本身也不能证明真实收款。此次没有查询生产收入、外部流量或已成熟用户 cohort，因此不能判断真实留存、付费意愿和产品市场匹配。

继续保留 WPCU official。下一轮实际关注：

- 发现→开始聊天、创建→确认首图、报价→交付→保存或再创作的完成率与流失点。
- Chat 首字/完整回复时间；图片/视频总交付时间与成品采用率。
- 同角色跨日回访、跨日创作、D1 / D7 留存。
- 生成失败退款、重复执行/扣费、客服介入率。
- 每次被采用的交付所耗设备时间/费用；真实付费接通后再看付费转化与毛利。

这些应由已存在的 Main 事实和 Metric Registry 承载。尚未定义的诊断指标先标为诊断并校准，不重新发起北极星迁移。小规模试用用于发现问题和形成基线，不凭少量样本宣称统计上的增长结论。

### 5. 交付基线和进度文档需要收敛

当前开发服务的启动 revision 为 `d270bfac…`，10:40 工作区摘要为 `9b56f5da…`。源码 watch / HMR 本来就会使工作树和启动标签不同；不能据此断言运行所有代码都陈旧，也不能将启动标签视为冻结生产证明。源码明确把 development 标为 `non-certifying-source-watch`。

建议结束当前几项关联工作后形成一个集成候选，把导航、Today、声音与 Chat/Gen 关联改动的证据归属对齐。在该候选执行适当的测试、构建、full readiness 和核心真实用户/运营回归。日常保持针对性验证；里程碑用冻结候选验收，减少持续边改边做昂贵全链复验的浪费。

进度文档也存在历史混杂：`CURRENT_FUNCTIONAL_COVERAGE.md` 有 808 行大量不同日期记录；`PRODUCT_PARITY_MATRIX.md` 的域级判定全部 pending；`LAUNCH_READINESS_AUDIT.md` 仍含旧 Chat 数据库与早期视频延期配置，当前覆盖末尾又引用它作为上线指引。历史证据应保留，但下一步需要一张简洁的当前能力表与最新证据入口，避免旧结论重新驱动开发。

## 建议的下一轮工作包

主线：**默认角色互动与创作链路的体验、效率和可复验性收口**。以下是依赖顺序，不是未经估算的日历承诺。

| 顺序 | 具体交付 | 完成条件 |
| --- | --- | --- |
| 0：形成基线 | 收尾已有 WIP，选定集成候选和实际默认模型/工作流 | 保留每项证据的版本；相关 CI 检查、运行认证与核心旅程通过；恢复清楚的问题有 owner |
| 1：五个样板角色 | 从现有角色中选择五个不同场景/风格，串起发现、聊天、图、声音、My AI 回访与完整 Create | 固定质量样本与源版本；身份/记忆/构图/声音问题有可复现对照；默认体验达到约定标准 |
| 2：默认链路性能 | 测量冷/热、排队和混合负载，优先改善最慢且最常用的路径 | 给出优化前后质量、耗时与设备成本；展示可信状态，刷新恢复不重复请求；容量边界明确 |

## 商业与完整平台如何继续

当前既定阶段尚不追求公开上线，不需要本轮立刻切 provider。真实购买仍然是阶段 A 未闭合的交付项：进入商业验收时，应独立完成 checkout、确认、权益、恢复原任务、到期与重新购买；Coin Store 则完成 offer、quote、一次支付、幂等 topup 和历史访问。受控加币不能代替它们。

进入公开发布时，再满足正式主站/受保护 Admin、HTTPS、存储、监控、队列隔离、必要 provider、备份恢复与目标环境验证。既定 `MODERATION_PROVIDER=mock` 继续按项目决策执行，保持年龄与基础拦截边界。

完整 OurDream 范围继续保留。后续按实际依赖和用户反馈推进：

1. 单人核心体验延伸：完整 conversation profiles、主动消息、Create 目录语义、生成高级参数与精确 Chat 交接。
2. 已有平台链深化：Feed / 作者 / 合集的发布、发现、互动和回访；帮助与支持、公开内容族的实际供给；商业环节与 Coin Store。
3. 新状态与结算域：双向 Voice Call、最多 12 角色 Group Chat、Packs / Comics、Creator Studio / 收益、Affiliate 归因与佣金。

这些分组是建议排序，不是删减 P1 要求，也不表示必须等前组全部完成才能处理有明确需求的后组。

现有剩余工作把 H3 修复列为最优先。我建议在项目总优先级上调整：默认链路已经覆盖更多日常用户任务，H3 应成为视频质量子任务。当前生产合同仍要求 H3，因此完整发布前该缺口仍需关闭，不能靠放宽门禁或改历史 pins 消失。
