# 英文场景保真：第一性原理诊断与修复方案

Status: in_progress
Type: task

本文是待实施方案，不修改现行 ADR，也不宣称场景质量修复完成。范围是英文产品旅程。当前建议：以现有图片 Product Action 和 `MomentSpec` 为落点，把场景解析、事实传递、像素生成分别验证；解析达到要求后，再复用于持续 Scene。先让一条真实图片链路正确，避免提前把未经验证的解析结果传播到所有聊天状态。

## 1. 必须保持的东西

用户要求“拍我们当前这一刻”，意味着：当前角色身份、当前已经成立的场景事实、这一次图片请求的明确要求，应当共同约束交付结果。一个漂亮且成功扣费的图片，不足以满足这个契约。

有三个不同的信息对象：

- **对话记录**：谁在什么时候说了什么。它包含事实、否定、提议、旧状态和错误复述，不能直接等同于当前场景。
- **Scene**：在该 Turn 的权威锚点上，当前已经成立的剧情状态。没有新证据的属性继续保留；被明确改变的属性被替换。
- **MomentSpec**：本次图片要呈现什么。默认继承当前 Scene；图片专属的时间、镜头或想象要求仅作用于此次图片，不自动写回剧情。

例子：`Maybe move it tomorrow` 不改变本子现在的位置；`Change our scene now ... right of the cup` 改变剧情位置；`Imagine a photo of this scene tomorrow morning` 改变图片要求，不表示剧情已经来到明天。助手合法完成的点蜡烛动作仍属于连续性，不能为了防止错误复述而丢掉全部助手记录。

## 3. 修复接口：一次图片动作形成一份可追溯的 MomentSpec

建议的主链路：

```text
Main 冻结的 Scene 锚点、有效对话来源、本轮用户请求
    → Chat 解析当前状态和本次图片要求
    → 候选 MomentSpec（事实 + 来源 + 未解决项）
    → Main 校验来源/版本/动作，冻结到原有图片 Product Action
    → Main 确定性编译必需事实 + 身份/造型 + 构图修饰
    → Gen
    → 按同一 MomentSpec 审阅成图
```

现有产品文档已经定义 MomentSpec、共享 assembler 和独立的 scene-adherence 质量维度，见[图片生成系统 §5.4、§7、§15](../../docs/product/CHARACTER_IMAGE_GENERATION_SYSTEM.md)。这里细化实现缺口，不另建一套世界状态数据库或 Generation Job。

### 3.1 解析一次，后续不再自由重写关键事实

在 Chat 的图片动作内，用一个明确的解析 module 接收完整的冻结输入，返回 `resolved` 或 `unresolved` 的候选 MomentSpec。它需要的最小信息是：

- 图中对象的局部 ID、外观/状态属性以及对象之间的关系；`notebook left_of cup` 必须保留两端对象，不能改写为“在角色左边”。这些 ID 用于该次解析和引用，不建立全局物体注册表。
- 时间/天气、地点，以及本次图片的衣着、取景等显式约束。
- 每条成立事实对应的有效消息 ID、消息版本/内容摘要和原文片段；标明由当前剧情继承还是本次图片要求覆盖。
- 未解决的指代、矛盾和缺失。模型自己给出的高置信度不清除未解决项。

角色 Soul 继续负责表达、情绪和角色声音；确认过的实体关系、时间及用户动作不再交给角色扮演文本重新组织。caption 可以自然表达，但不得把生成提交写成已收到成图。

**这里最难的仍然是自然语言解析。** 来源片段能证明“确有此话”，不能机械证明时态、否定、实体指代与关系解释正确。JSON schema 也不能证明没有漏事实；让同一个模型列事实、再声称自己覆盖完整，不构成独立验证。候选必须通过英文金标准和未见用例后才能进入正式运行。

已有独立提示、事实数组和 Qwen 对照没有过门。因此不把“换成解析提示”当作已修复。先在现有唯一模型 route / adapter 下评估这个职责；若能力不足，离线比较其他可运行的自托管候选。不能凭模型名或大小认定合格，也不提前指定未经验证的替代模型。正式引入独立解析模型 route 时，须显式修订 [ADR-21](../../docs/architecture/21-companion-chat-deep-runtime.md) 的唯一 Chat route 约束；不能暗加第二套配置或 runtime。

### 3.2 更新必须作用于属性，且保留来源语义

最低必过例的期望状态：

| 输入/变化 | 必须得到的结果 |
| --- | --- |
| 原始真实英文用例 | 雨夜；单本蓝色闭合笔记本平放木窗台；本子在白杯左侧；本子不在用户手中；本次图为角色穿衣半身图 |
| 助手说 dusk、用户拿着本子 | 用户已确立的雨夜和本子位置继续有效，不能采用矛盾复述 |
| 用户明确改成晴天，把本子移到杯右侧 | 只替换时间/天气和相关位置；仍是原来的蓝色闭合本子，仍平放窗台，不新增第二本 |
| 明天移动的提议、否定已完成动作 | 提议不成为现在的位置；`not planted` 不成为已种植 |
| 助手明确点燃蜡烛 | 合法角色动作成立，不被“一律只信用户文本”丢弃；原有本子与杯继续存在 |
| 本次图想象明天晴天，聊天仍在雨夜 | MomentSpec 使用图片要求，剧情 Scene 不因此改变 |
| 精确标签、多个相似物件、关系的等价反写 | 标签逐字保留；不合并不同物件；“杯在本子右边”等价于“本子在杯左边”，不能词面误判 |

来源优先级需要与动作语义结合。不能无条件采用“最新一句话”或“用户永远覆盖一切”：旧记录可能包含未改变的属性；助手可能合法改变自己可控制的物体；用户也可能只是在引用、提问或设想。

### 3.3 Main 冻结语义输入，编译器承担无损传递

沿用现有 `turn_action`、attachment、Generation Request/Attempt 和 MomentSpec JSON 存储：

- Main 对照冻结执行快照校验 source refs、版本、引用内容、当前 attempt 和动作授权。源码中已有幂等预留不能变成重复创建 Job。
- 在首次请求图片效果时冻结候选的 MomentSpec 及其 digest。原键重播、超时恢复和 assistant regenerate 返回或复用该动作已经冻结的内容；不得在恢复时重新解释成另一个画面。
- 与当前隐式 `promptHint` 直通路径原位整合。渲染 prompt 由程序从冻结 MomentSpec 生成；已结构化的时间、物体属性和关系没有第二次自由文本“润色”步骤。
- 先分配必需事实与身份所需预算，再分配可选修饰。每个必需 fact ID 都应能追踪到最终发送内容；必需内容超出 route 实际预算时，返回明确的未解决/编译失败，不能静默截断、丢弃或改成空默认场景。压缩可选文字后仍超限，才进入该失败路径。
- 必需语义未解决时停止图片预留和 Gen 消费，使用现有可恢复失败路径。结构校验不能保证抓住每一种语义错误，未检测到的错误仍由模型评估与结果审阅发现。
- 新来源与 MomentSpec 中的聊天内容必须覆盖现有删除/隐私清理路径，尤其是 `turn-ledger.ts` 的图片来源清理；不可只清 `promptHint` 而留下新增原文副本。

`source refs + deterministic compiler` 能明确保证的是有效来源绑定和已接纳事实的传递，不是开放域理解百分之百正确。

### 3.4 成图按同一份语义输入检查

用人工确认的 MomentSpec 直接走实际 Main assembler、同一身份参考和 Gen route，是隔离像素层的实验。不能只发一段简化 prompt 或绕过角色身份模板，然后宣称真实路径可用。

先验证原始场景与明确更新这两个失败类型，逐张检查：昼夜/天气、物件数量和状态、相对关系、支撑面、取景、角色身份。保留失败结果，不换 seed 挑成功。

若正确的最终输入仍画错，则再针对 workflow/reference/图像模型做单变量比较；区域控制、布局或编辑约束只在这个证据支持时采用。它们不是文本 JSON 自动变成像素保证的捷径。也不能未经校准就加一个视觉模型评分，或改变既有 Intent 失败的保留图/纠正重试政策来掩盖错误。

## 4. 实施顺序与完成判据

1. **固定故障与期望。** 保留现有六个英文用例和真实失败原件，补上图片专属覆盖、否定/提议、实体消歧、合法角色动作及等价关系。模型解析、程序编译、真实像素分别有各自的判断结果。本轮已完成代码接口的离线红灯复现，尚未完成新的解析器或渲染验证。
2. **先做一条图片动作的完整切片。** 解析候选 → Main 校验冻结 → MomentSpec 原位持久化 → 确定性编译；普通聊天 Scene 先不接收未经资格验证的解析结果。控制新增解析延迟和模型调用次数，失败不无限重试。
3. **分别证明两个能力。** 原文 → MomentSpec 必须通过冻结例和未参与调整的英文用例；人工确认的 MomentSpec → 真实图必须通过原始/更新场景。合格之后组合运行 Main→Chat→Gen，而非用其中一边的成功替代另一边。
4. **补产品恢复验证。** 同源验证本轮包含场景修改的图片请求、重播、assistant regenerate、图片 retry、取消/删除、交付、持久化与唯一扣费。解析/编译未解决不能启动收费生成。
5. **复用于持续 Scene。** 图片切片已证明解析可用后，用同一解析逻辑替换 `scene.ts` 中被证实不能承载的部分。保留 Main Turn 权威；edit/regenerate 从原 Scene 锚点计算一次，失效来源重建。不新增 Chat 数据库或同步依赖异步 igrep 投影。旧空 Scene 不能被升级为“已知完整”：从有效来源重建，不完整时保留未解决状态。

冻结例全部通过只是必要条件，不证明开放域稳定；记录未见例错误类型、重复运行波动、解析延迟、成本和像素限制。正式完成仍要求绑定同一 source revision 的真实链路与直接成图审阅。

## 5. 当前取舍

加正则、继续叠提示、直传全历史都已经产生明确反例，不再作为默认修复路径。第一步的工程重点是把已有 MomentSpec 做实，使每个错误能定位在理解、传递或像素生成中的具体一层。模型资格验证不能被省掉；若当前可运行模型达不到解析要求，应把该能力缺口明确保留，而不能用规则堆叠和成功样本遮盖。

本轮只增加 task-local 诊断与这份方案，正式运行代码、模型 route、服务、数据库及生成配方均未修改。
